# Row-owned recursive forest populations

`RecursivePopulationRequest` and `RecursivePopulationRecipe` provide a distinct terminal population mechanism for #28. They do not enter the `FrozenFunction` registry. The existing frozen forest adapter still rejects `fresh-forest-per-row`.

[MITRA v1 Algorithms 3–5](https://arxiv.org/html/2510.21204v1#A1.SS2.SSS2) and the retained core source audit distinguish the prose's reusable frozen function from Algorithm 5's forest construction inside the row loop. This envelope preserves that row-loop interpretation. Tree construction still selects the separately named prose/Algorithm 4/r0-extension plan; using an ancestor DAG, keyed population comparison streams, declared vocabulary and target coordinate are explicit r0 integrations, not a claim to reproduce the complete MITRA prior.

A request declares an authored functional, native, heterogeneous-vector or converted ancestor DAG, ordered `(node, encoded-state-channel)` parent slices, and a per-row forest plan whose `populations` equals the ancestor task row count. Observed features retain the ancestor readouts and typed schema. Categorical observations remain integer vocabulary codes while forest parents receive the graph's encoded states. No discarded ancestor target adapter is evaluated. The forest emits raw regression means or actual int64 majority labels; winner indicators in `scores` are explicitly not probabilities. All regression output coordinates are retained, with one declared target coordinate. No query calibration, variance normalization or label adapter is added.

`realize_recursive_population(request, seed=..., task_id=..., rng=...)` retains the complete sampled forest receipt, ordered parent rows, observed rows and exact integer identity. The optional injected construction generator is owned atomically through final custody verification; omitted generators use a deterministic independent construction key. The core's initial/final snapshots and complete raw draws remain inside the archive. Generation and decoding replay those records and verify the ancestor rows. A changed seed/task identity is rejected by frozen generation: construct a new realization explicitly. A changed row count requires a new request with consistent ancestor task and plan population sizes. Repeated or reordered inspection indices select from the original full population rather than rebinding forests to selected rows.

`intervene_recursive_population` composes an existing matched `CausalInterventionRecipe` over the exact ancestor graph, or an explicit terminal target clamp. Matched mode retains all original forests and row ownership. Population mode uses distinct fingerprint-keyed ancestor and forest streams with a declared population identity; the original baseline archive remains nested unchanged. Intervened parent and observed rows are retained and replayed. Categorical clamps bypass terminal traversal; a full scalar regression clamp also bypasses it. Partial vector target clamps retain the other coordinates and disclose the raw mean plus clamp in inspection. `generate_recursive_population_pair` returns both ordinary training tasks and an explicit equality/ownership card. It does not promise variance matching.

The shared `generate_task`, `recipe_from_dict`, `explain_generation` and generation archive APIs accept these realized versions. Inspection includes original encoded ancestor states, declared parent slices, each row-owned tree path and reached leaf, aggregation or explicit clamp, and direct target emission. The existing generation graph column window is preserved. Reopening checks complete required fields, primitive identity types, row custody, raw construction replay and semantic task metadata. Execution implementation identity is checked; descriptive historical environment fields are not used to refit or alter a task.

Admission reserves worst-case forest construction and raw records together with ancestor geometry/work, retained row matrices, replay copies and inspection buffers before construction snapshots. Archive decoding reserves population work before nested ancestor or forest replay. Caps are conservative estimates, not measured RSS or a claim that all Cartesian combinations fit default limits. Insufficient capacity rejects; no clipping or retry changes the law.

## Required follow-ons

This slice supports one terminal population forest over an arbitrary supported ancestor DAG. Multiple row-owned forest mechanisms inside a DAG, descendant mechanisms after them, sampled graph catalog selection, guarded workbench/Colab controls, complete source hyperparameter catalogs and scientific/resource/GPU evaluation remain required separate work. Frozen-function and population lifecycles are never silently substituted. CPU is explicit; no hosted or GPU acceptance is claimed. Author evidence is gitignored under `docs/evidence/issue-28-recursive-population/`; independent review and combined release checks are separate.

Inspection validates tensor dtype, layout, shape, device, gradient status and values against replay, plus exact source/episode/task/schema metadata. Ordinary noncontiguous strides remain valid, including tensors materialized from archives. The recipe record requires exactly its declared fields and primitive identity types; duplicate JSON fields are rejected at every nesting level. Execution implementation identity and field schema are semantic. Historical Python/NumPy/Torch versions, available hardware descriptions and thread counts may differ when they retain their declared primitive types; inspection preserves those descriptions and does not treat them as evidence of a new hosted/GPU execution.
